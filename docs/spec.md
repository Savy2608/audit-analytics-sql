# Audit Analytics in SQL - Specification

## 1. Goal

Build a small, complete audit-analytics project in three parts:

1. Generate a synthetic accounts-payable dataset with known fraud and control failures planted in it.
2. Detect those failures with plain SQL checks.
3. Measure how many of the planted cases each check catches (recall) and how much noise it adds (precision).

Because the answer key is known, every check is scored instead of judged by eye. The focus is on
evaluating controls at scale with Python and SQL.

Ground rules:

- All data is synthetic, generated by code from a fixed seed. No real company data is used or imitated.
- Everything in the repository (code, comments, console output, file names, documentation) is in English.
- Keep it small: no web UI, no cloud services, no extra frameworks.

## 2. Stack and repository layout

PostgreSQL 16 holds the data and runs the checks. Python generates the data and drives the run.
Each check is a plain `.sql` file, so it can be read on GitHub without running anything.

```
audit-analytics-sql/

│   ├── 01_duplicate_payments.sql
```

Database options: `docker compose up -d`, or any existing PostgreSQL 16 server. Connection
settings come from `.env`. Only `.env.example` is committed, never `.env`.

Run order: `python generate_data.py`, then `python run_checks.py`, then read `results/scorecard.csv`.
The whole pipeline must finish in under a minute.

## 3. Data model

One fictional company, calendar year 2025. Every date in the dataset falls inside 2025. All IDs are
text with a table prefix (`E`, `V`, `INV`, `PAY`, `JE`), so a single `record_id` is unique across
all tables.

| Table | Default rows | Columns |
|---|---|---|
| `employees` | 60 | employee_id, name, department, role, address, bank_account, approval_limit_usd |
| `vendors` | 200 | vendor_id, name, address, bank_account, status, created_date, inactive_date |
| `invoices` | 8,000 | invoice_id, vendor_id, invoice_number, invoice_date, amount_usd, created_by, approved_by, approved_date |
| `payments` | about 7,700 (derived) | payment_id, invoice_id, vendor_id, payment_date, amount_usd |
| `journal_entries` | 15,000 | entry_id, entry_datetime, account, amount_usd, source, created_by, approved_by, description |

Columns that the checks depend on:

- `employees.role`: one of manager, ap_supervisor, ap_clerk, accountant, staff. AP clerks enter invoices, accountants post journal entries, and managers and AP supervisors approve.
- `vendors.inactive_date`: the business day a vendor was closed. It is set if and only if `status = 'inactive'`.
- `journal_entries.source`: `manual` or `automated`. Check 4 deliberately does not trust this label.

The payment count is derived, not set. Most invoices are paid 7-21 days after the invoice date.
Invoices issued late in December are still unpaid at year end.

Realism rules:

- Amounts follow a log-normal distribution, so first digits closely follow Benford's Law.
- Most activity happens on weekdays in business hours. A small share of journal entries is posted in the evening (before 22:00) or on weekends.
- There is a single approval threshold of 5,000 USD. Invoices above it are approved by a manager; smaller ones by a manager or an AP supervisor. Background data is never approved by the person who entered it.
- Vendor activity is skewed (log-normal vendor weights): some vendors bill much more often than others.
- Bank account values are obviously fake strings (`FAKEBANK-` + 10 characters), never real formats.

## 4. Audit checks and planted anomalies

The generator plants a fixed number of cases per check and writes every planted ID to
`data/ground_truth.csv` (check_name, record_id). It also plants near-misses: legitimate records that
look similar and must not be flagged. These go to `data/near_misses.csv`. Near-misses force the
checks to be precise, not just broad.

| # | Check | Risk | Rule | Planted cases | Near-misses (must not flag) |
|---|---|---|---|---|---|
| 1 | Duplicate payments | Paying the same bill twice | Same vendor, same amount, paid within 7 days (`LAG()` over vendor and amount) | 25 second payments of an already-paid invoice, 1-7 days after the first | 3 vendors with monthly invoices of the same amount, paid about 30 days apart |
| 2 | Split invoices | Splitting a purchase to stay under the 5,000 USD limit | 2+ invoices from the same vendor, entered by the same clerk in the same calendar week (Mon-Sun), each under 5,000, total over 5,000 (window `SUM()`) | 15 groups of 2-4 invoices | 10 groups with the same vendor, clerk and week whose total stays under 5,000 |
| 3 | Self-approval | Segregation-of-duties failure | `created_by = approved_by`, joined to employees | 20 invoices and 20 journal entries | none |
| 4 | Weekend / round entries | Manual entries outside the normal process | (Saturday/Sunday OR 22:00-05:59) AND amount is a multiple of 1,000 (`EXTRACT(dow)`, hour, modulo) | 30 entries: half on weekends, half at night (before or after midnight) | Automated month-end entries on Saturday 23:30 with non-round amounts; round accruals on weekdays in business hours |
| 5 | Vendor-employee match | Fictitious vendor set up by an employee | Vendor address (after normalising case and whitespace) or bank account equals an employee's | 5 vendors: 3 share an address (one typed in upper case), 2 share a bank account | none |
| 6 | Payments to inactive vendors | Paying a vendor that should be closed | `payment_date > inactive_date` | 12 payments after the vendor's inactive date | 8 payments shortly before or on the inactive date |
| 7 | Benford first-digit test | Fabricated amounts in bulk | For each employee with 100+ manual entries, chi-square of first digits vs Benford (8 degrees of freedom) > 20.09 (p < 0.01), computed in SQL | One accountant's 300 entries with first digits skewed toward 5-9 | none |

Check 7 flags a population (an employee), not individual records. It is scored as caught or missed
for that employee.

Rules for planting:

- Planted cases and near-misses go into slots that do not collide with background data. For example, a split group is placed in a vendor/week with no other invoices, so the labels stay clean.
- One check's planted cases must not trip another check. For example, duplicate payments are only planted on active, non-recurring vendors.

## 5. Evaluation

`run_checks.py` runs in this order:

1. Create the database if it is missing, then recreate the schema.
2. Load the CSVs with `COPY`.
3. Print row counts and a reconciliation. The gap between invoice and payment totals must be fully explained by unpaid invoices minus overpayments, and every payment must match its invoice's vendor and amount. If not, the run stops before any check executes.
4. Run each check and save its output to `results/<check>.csv`. Every check returns `record_id` plus context columns.
5. Compare the flagged IDs with the answer key and write `results/scorecard.csv`.

The scorecard has one row per check with these columns: planted, flagged, true_positives,
false_positives, missed, precision, recall, near_misses_flagged.

Honesty rules:

- Report the scorecard exactly as produced. Keep false positives visible and explain them in the README.
- Do not tune queries to the answer key. A rule may only change for a reason that comes from the risk itself, and that reason must be documented.
- Never type numbers into the README by hand. `python run_checks.py --update-readme` writes the summary, the checks table, the scorecard and the examples from a real run of the committed dataset.
- The README gives one trade-off per check: what a tighter rule would miss, and what a looser rule would add.

## 6. Scale benchmark

`benchmark.py` checks that the queries still work at a realistic size:

- It generates about a million rows with the same seed, keeping the default ratios: 2,000 employees, 7,500 vendors, 300,000 invoices and 410,000 journal entries. The data goes into a temporary directory and is never committed.
- It runs the reconciliation gate and scores every check.
- It times every check (median of 3 runs after a warm-up), first without the secondary indexes and then with them.
- It saves `EXPLAIN (ANALYZE, BUFFERS)` output for check 1 in both states.
- Results go to `results/benchmark.csv`. `--update-readme` writes the README's Scale table from that run.

## 7. Engineering rules

- **Reproducible:** the seed (default 42) and table sizes are CLI options, and the same seed always produces byte-identical CSVs. Package versions are pinned, because Faker output can change between versions.
- **Readable SQL:** one check per file, CTEs with clear names, and a 3-5 line comment at the top stating the risk, the rule and the threshold. No clever one-liners.
- **Tests (pytest, on a tiny generated dataset in a separate database):**
  - generator determinism, requested sizes, planted counts, and every date inside 2025
  - each check flags exactly its answer key on the tiny dataset; the split-invoice check, which has legitimate false positives, is instead compared with an independent pandas implementation of the same rule
  - near-misses are never flagged, and boundary cases are covered (payment on the inactive date, entries after midnight)
  - scorecard math
- **CI:** GitHub Actions runs on every push and pull request. It runs pytest against a Postgres 16 service, then reruns the full pipeline and fails if `data/` or `results/` differ from the committed files.

## 9. Design decisions

Decisions made during the build, and why:

- **Split invoices are grouped by clerk as well as by vendor and week.** The risk is one person avoiding the approval limit, and that person is the one who enters the invoices. Grouping by vendor and week alone flagged roughly six times as many invoices on the default data, because busy vendors legitimately send several invoices a week. The remaining false positives are kept and explained.
- **Vendor weights are log-normal, not Pareto.** An early Pareto version gave a single vendor almost a quarter of all invoices, which is not realistic. The change was made for realism, not to improve any score.
- **Near-misses are stored separately** (`near_misses.csv`) so the tests can assert that they are never flagged.
- **Check 4 ignores the `source` label**, because a mislabelled manual entry is exactly what the check should catch.
- **The reconciliation is a hard gate**, so no check ever runs on data that does not tie out.
- **Check 5 uses two equality joins instead of one `OR` join.** The benchmark showed that `ON address = ... OR bank_account = ...` forces a nested loop over every vendor-employee pair. Two equality joins combined with `UNION ALL` can use hash joins and return the same rows.
